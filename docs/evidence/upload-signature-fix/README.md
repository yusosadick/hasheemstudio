# Live guest upload signature repair — 2026-10-11

The exact owner failure was reproduced at `https://hasheemstudio.com` in Chromium with the
repository's generated 5-second H.264/AAC MOV. The owner supplied a screenshot, not the source
video; no owner media was inspected or uploaded.

Root cause: the API's `api-gw` Docker DNS alias was shared with another project's gateway on the
external ingress network. Repeated real DNS lookup from the Studio API returned both gateways.
Calls reaching Studio succeeded; calls missing Studio produced the exact signature error. Studio
JWT configuration hashes matched across API/worker/gateway/Storage/Auth/PostgREST, and the
service-role JWT's HS256 signature and expiry were valid. See `reproduction.json`, `before.png`,
`dns-before.json`, `config-before.json`, and `log-boundary.json`.

The functional change is only `API_STORAGE_HOST: hasheemstudio-envoy`. No credentials, JWT
verification, RLS, bucket privacy, frontend, worker, quotas, migration, shared proxy, or other
project resource changed. The real-DNS regression fails on the old source configuration and
passes on the new configuration and deployed runtime.

policy; no application endpoint deletes that metadata, and no direct SQL deletion was performed.
No owner objects/accounts were touched.

## Scope, rollback and remaining limits

`review.md` records the scoped source-first security review, evidence, retained controls and gaps.
No naturally expired user JWT or owner-device/network was exercised. This is not a whole-host audit,
historical credential-access investigation, or guarantee against hacking.

Read-only follow-up discovery found a preexisting proxy pin drift: API_TRUST_PROXY is `10.0.1.6`,
while current `coolify-proxy` is `10.0.1.7`. The upload-signature release preserves that setting.
Its impact on per-network guest accounting needs a separately scoped correction/verification;
this release does not claim complete proxy/rate-limit correctness. See STATUS/DECISIONS.

Rollback material: previous immutable image above; exact prior resolved API configuration in
`tmp/upload-fix/rollback.compose.json` (0600). A full configuration rollback would restore the
known-bad hostname, so prefer retaining the fixed hostname if only an image rollback is necessary.
No rollback, credential rotation, DNS/firewall change, or database restore was performed.
